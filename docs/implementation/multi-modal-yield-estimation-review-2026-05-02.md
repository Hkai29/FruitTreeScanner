# 多模态融合产量估算计划审查（2026-05-02）

## 审查结论

该计划结构清晰、模块拆分合理，但在**可执行性、精度闭环、性能预算与验收标准**方面仍缺少关键约束。当前版本适合作为“方案草图”，不适合作为直接开发排期依据。

---

## 关键问题（按优先级）

### P0（阻断上线）

1. **检测模型定义不一致**
   - 文档写到可使用 `VNRecognizeAnimalsRequest` 或自定义水果模型，但两者语义差异巨大（动物识别无法直接用于水果类别）。
   - 建议：明确唯一路线（推荐自定义 CoreML），并在计划中删除动物识别分支，避免实现偏航。

2. **融合匹配缺少相机几何与坐标系约束**
   - “2D 反投影到 3D”未定义使用的相机内参、深度对齐方式、坐标系（camera/world）与时间同步策略。
   - 建议：补充 ARKit frame 时间戳对齐规则、外参来源、以及误差预算（例如重投影误差阈值）。

3. **计数权重缺乏标定依据**
   - `fused=1.0 / imageOnly=0.5 / cloudOnly=0.3` 为经验值，未给出验证集校准流程。
   - 建议：将权重设为可配置参数，并通过标注数据集做网格搜索或贝叶斯优化得出初始权重。

### P1（高风险）

4. **DBSCAN复杂度与移动端实时性未量化**
   - 计划未给出每帧点数上限、聚类周期、延迟预算。
   - 建议：定义性能 KPI（如 100k 点输入，聚类 <120ms，主线程占用 <5%），并说明降采样策略（体素网格/ROI 裁剪）。

5. **缺失防重复计数机制**
   - 当前流程按帧输出候选，未定义跨帧关联（tracking），容易重复计数。
   - 建议：增加 `FruitTrack`（ID 持久化、生命周期、合并策略）并在 `FruitCounter` 前做去重。

6. **尺寸先验过于刚性**
   - `0.04m~0.15m` 对不同品种、成熟度、采集距离可能不稳。
   - 建议：按 `FruitCategory` 配置动态尺寸区间并支持现场标定。

### P2（改进项）

7. **测试计划过粗**
   - 缺少可量化验收指标。
   - 建议补充：
     - 检测：mAP@0.5、召回率；
     - 聚类：候选召回/误检率；
     - 融合：匹配精确率；
     - 端到端：MAE/MAPE（与人工计数对比）。

8. **缺少失败模式设计**
   - 如逆光、遮挡、风扰动、密集果簇等场景无降级策略。
   - 建议：定义场景标签与回退策略（仅点云计数 / 仅图像计数 / 暂停输出）。

9. **模型与数据治理未定义**
   - 未说明训练数据来源、类别分布、标注规范、版本管理。
   - 建议：新增 `Model Card` 与 `Dataset Card` 最低要求。

---

## 建议补充到计划中的“可验收定义”（DoD）

- 设备：iPad Pro LiDAR（列明芯片代次与 iOS 版本）
- 性能：扫描时平均 FPS ≥ 20，端到端结果刷新周期 ≤ 1s
- 精度：
  - 单树总数 MAPE ≤ 15%
  - 大果类（苹果/橙）召回率 ≥ 85%
- 稳定性：连续扫描 10 分钟无崩溃、内存峰值 < 1.5GB
- 回归：不影响现有 PLY 导出与历史记录功能

---

## 推荐的最小实施顺序（可落地）

1. 先实现 `PointCloudCluster + Track 去重`（离线回放验证）
2. 引入 `ImageDetector`（先低频推理，确认热/功耗）
3. 落地 `FusionValidator`（先最近邻 + 置信度融合）
4. 最后做 `FruitCounter` 权重标定与 UI 输出
