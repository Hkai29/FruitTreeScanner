## 按严重程度排列的发现

### 1. P1：保存失败后没有可走通的重试路径

- `FruitTreeScanner/Views/ScanView+Export.swift:33`：PLY 导出失败只清除 `isEstimating` 并显示提示，生命周期仍是 `.finishing`。
- 同文件第 45–55 行：结果文件保存失败后依然展示结果，只在成功时进入 `.completed`。
- `FruitTreeScanner/Views/ScanView+State.swift:24`：完成/导出只允许 `.recording` 或 `.userPaused`，因此失败后的 `.finishing` 被拒绝。
- `FruitTreeScanner/Core/ScanCoordinatorWorkflows.swift:302`：估算快照已清空活动检测和归档检测；简单地重新估算也不能保证恢复原来的证据。

用户后果：遇到磁盘写入失败等情况，看到“重试导出”的提示，却不能通过完成按钮重新保存。结果页的返回/继续也没有重试保存动作。

修复方向：保存失败保留冻结的点云、结果和文件身份；提供重试保存操作，只重试失败阶段。为 PLY 写入失败、结果写入失败和重试成功补充流程测试，不能只测试底层写入事务。

### 2. P1：停止/完成时会丢弃已经开始推理的同一扫描帧

- `FruitTreeScanner/Core/ScanCoordinatorWorkflows.swift:51`：推理完成后要求证据门仍打开且 generation 一致。
- 同文件第 215、225 行：停止和进入完成状态均关闭证据门。
- `FruitTreeScanner/Core/ScanCoordinator.swift:353`：每次改变证据门都推进 generation。
- `FruitTreeScanner/Core/ScanCoordinatorWorkflows.swift:60`：flush 等待正在运行的任务，但该任务已在上述检查中丢掉检测结果；随后只处理队列中尚未消费的帧。

用户后果：同样的扫描，点击停止的时机会影响最后一帧是否计入。若它正好是建立稳定轨迹所需的第二次观察，可能少算该果实。不是所有扫描必然受影响，取决于停止与推理完成的时序。

修复方向：停止接收新帧与丢弃旧扫描结果采用不同规则；允许正常停止前已接纳的同一扫描任务提交结果。系统中断、取消和新扫描仍必须拒绝旧任务。补充受控的在途推理测试。

### 3. P1：总产量的可靠性标签没有充分反映重量测量质量

- `FruitTreeScanner/Core/ScanYieldEstimateHelpers.swift:22`：融合加权证据达到 5 就设为 high，否则 medium。
- 同文件第 117 行：单果几何评估收到固定的 `validDepthRatio: 1`，并非真实有效深度比例。
- 同文件第 126 行：没有匹配几何候选时使用平均单果重量。
- `FruitTreeScanner/Core/YieldResultComposer.swift:416`：最终置信度沿用融合证据和覆盖率调整，没有汇总单果重量警告、平均重量回退比例或校准误差。
- `FruitTreeScanner/Views/ResultPresentationModels.swift:150`：通过现有检查后展示“结果可靠，可用于估产”。

用户后果：识别到果实并不等于测准了重量。若尺寸测量偏差很大、小果实几何证据不足或使用先验重量，仍可能得到正面的总产量可靠性标签。

修复方向：分开展示果实存在/计数证据与重量可信度；把几何质量、回退占比、校准样本和实测误差纳入总结果。继续保留仅 fused 参与可靠估产的规则。

### 4. P2：扫描期间主线程反复重建历史轨迹

- `FruitTreeScanner/Core/ScanCoordinatorWorkflows.swift:91`：检测结果在 MainActor 中追加并调用归档。
- 同文件第 112–135 行：每批结果重新从检测集合构建稳定轨迹，再对整个归档集合压缩。
- `FruitTreeScanner/Core/DetectionDeduplicator.swift:244`：每条检测线性寻找兼容轨迹；第 179 行又线性比较已有归档轨迹。匹配还可能做深度采样和三维投影。

用户后果：目标多、轨迹多时，界面和扫描控制会与证据整理争用主线程。360 帧保留上限限制了部分内存，但没有限制每次主线程工作的耗时，归档也不是固定数量上限。

修复方向：后台串行维护增量轨迹，缓存每次检测的三维位置，只把摘要发布到主线程。以真实 30/60/120 秒扫描记录主线程耗时、帧率、峰值内存和温度。当前未测得实际卡顿时长。

复核更正：普通完成流程先导出并缓存去噪点云，因此不能把 `makeAnalysisPoints()` 的主线程缓存未命中路径描述为每次完成都会发生的卡顿。

### 5. P2：旧校准数据会跨算法/模型版本继续生效

- `FruitTreeScanner/Core/CalibrationRecord.swift:5`：记录只有树 ID、日期、估计值、真值和水果类型，没有模型、参数或算法版本。
- 同文件 `YieldCalibrationCorrector.correction` 按水果类型筛选，`ScanFruitConfiguration.capture` 会读取这些记录并自动生成本次修正系数。
- `FruitTreeScanner/Core/ScanResultExportService.swift:271` 导出模型名称，但名称不能唯一标识模型权重；当前结果缺少完整版本身份。

用户后果：升级检测模型或修改估产算法后，旧算法产生的偏差系数仍会修正新结果，可能把改进后的估算再次拉偏，也不便于解释历史误差变化。

修复方向：校准记录绑定估算基线和模型/参数版本，并明确记录估计值是否已经校准。兼容性不明的旧数据保留供查看，不自动套用。

### 6. P2：YOLO 输出兼容逻辑有可确定的边界错误

- `FruitTreeScanner/Core/ImageDetectorYOLOParser.swift:32` 起，只要第二维大于等于 5 就认定为通道轴。对于 `[1,2100,30]`，会误把 2100 当通道数，从而触发标签契约拒绝，而非正确识别转置布局。
- `FruitTreeScanner/Core/ImageDetectorYOLOSupport.swift:93` 起，把像素坐标固定除以 320；640 输入的像素输出会得到错误框。

这是模型替换/导出格式改变时的兼容问题，不能据此断言当前捆绑模型的每次检测都错误。

修复方向：依据模型输入尺寸和标签数量验证张量布局，分别覆盖两种轴布局和 320/640 输入，拒绝真正不兼容的输出。

### 7. P2：CI 不能在 PR 阶段阻止核心行为回归

- `.github/workflows/build-ipa.yml` 只有 main 的 push 和手动触发，没有 pull_request。
- 工作流执行 simulator build，没有 xcodebuild test，也没有真实果园验证门槛。

用户后果：编译成功的融合、保存或生命周期错误可以进入 main。现有测试文件包含约 472 个 `func test` 声明，但本次不能把它们视为已执行通过。

修复方向：先恢复可用 iOS Simulator runtime，PR 运行关键逻辑及全量 XCTest；真机扫描验收作为发布前独立门槛。

## 为什么仍不足以称为成熟的估产应用

仓库已有真机验收和 ground truth 协议，也有训练数据审查资产。这说明已经有质量意识。但本次在检查的验证目录中看到的是协议和模板，未取得绑定当前模型、参数和 App 版本的真实果园验收结果；不能据此声称当前版本的误差率或现场完成率已达标，也不能断言仓库之外不存在实测。

应先收敛一个水果/场景，实测同一棵树的重复扫描、人工果数和实际重量，按光照、遮挡、距离统计失败和偏差。图像检测指标不能代替整棵树计数误差，更不能代替公斤数误差。

现阶段最优先的顺序：

1. 打通保存失败恢复，修正正常停止时的在途证据交接。
2. 让重量可靠性标签诚实反映测量和校准质量。
3. 真机量化扫描性能，针对数据解决主线程瓶颈。
4. 建立当前版本的果园真值报告和 PR 测试门槛，再扩展功能或支持类别。
