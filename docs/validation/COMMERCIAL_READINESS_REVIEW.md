# FruitTreeScanner 商业级现状评估

评估日期：2026-07-02  
评估目标：停止“无休止小修”，判断当前 App 到底是什么状态，以及怎样才真正接近商业级产品。

## 结论

FruitTreeScanner 现在不是玩具 Demo，也不是纯 UI 壳。它已经是一个功能覆盖较广的专业原型 / MVP：有 LiDAR 扫描、点云导出、扫描质量提示、CoreML/点云估算链路、历史记录、标签地块、校准、批量导出和较多单元测试。

但它还不是商业级生产 App。原因不是“还差几个按钮”，而是商业级的核心证据链还不完整：

1. 产量/果数估算缺少真实果园 ground truth 验证。
2. 扫描流程还没有证明普通采集员在真实现场能稳定完成。
3. 真机 LiDAR、长时间扫描、弱光/强光、后台切换、低电量、热降频等现场条件还没有形成验收矩阵。
4. 仓库混合了 App、训练 runs、论文、研究 skill、数据集、DerivedData，工程边界不像可维护商业产品。
5. CI 存在，但主要是编译/打包雏形；还没有形成 TestFlight、签名、崩溃收集、性能门槛和发布流程。

一句话判断：现在最应该做的不是继续加功能，也不是继续随机修小 bug，而是冻结主流程，建立“真实设备 + 真实果园 + 可量化误差 + 发布质量门槛”的证据闭环。

## 评估依据

当前仓库显示 App 主体已经比较完整：

- `FruitTreeScanner/Core/` 包含扫描协调、Renderer、点云解析、聚类、融合估算、导出、历史、标签、设置等核心逻辑。
- `FruitTreeScanner/Views/` 包含首页、扫描页、结果页、历史、点云查看、导入、批量导出、地图、标签、校准、设置等页面。
- `FruitTreeScannerTests/` 目前有 15 个测试文件，覆盖导出、点云处理、检测去重、估算、诊断、readiness、HUD 状态等。
- `README.md` 已经定义了面向果园 LiDAR 扫描的产品愿景。
- `.github/workflows/build-ipa.yml` 有 iOS 构建/IPA 打包雏形。
- `docs/superpowers/specs/2026-05-06-commercial-grade-enhancement-design.md` 已经指出性能、线程安全、GPU/CPU 同步、扫描交互和架构拆分问题。
- 仓库曾经在根目录同时包含训练 runs、数据集、论文和本地工具资产；现在已收拢到 `ml/`、`research/`、`tools/` 和 `docs/`。

## 商业级定义

商业级不是“看起来像产品”，而是满足以下标准：

1. 用户能稳定完成一个清晰工作任务。
2. 输出结果有可解释、可复核、可量化误差。
3. 出错时不会丢数据，用户知道如何恢复。
4. 真实设备和真实环境下有质量门槛。
5. 工程仓库、发布流程、隐私合规、客户支持能长期维护。

FruitTreeScanner 的核心商业任务应该收敛为：

选择树体/地块 → 扫描果树 → 判断扫描质量 → 估算果数/产量 → 保存记录 → 复核/导出报告。

任何不服务这条链路的功能，都应该降级为后续版本，而不是继续堆到首页和扫描流程里。

|---|---|---:|
| 产品定位 | 果树 LiDAR 扫描方向明确，但首页功能较多，主线仍需收敛 | 6/10 |
| UI 视觉 | 首页和深色系统已经有专业感，卡片和图像资产较完整 | 7/10 |

| 算法可信度 | 有融合估算和测试，但缺少真实采摘/称重 ground truth 验证 | 3/10 |
| 数据闭环 | 历史、标签、导出、地图、批量能力较丰富，但备份/迁移/恢复不足 | 6/10 |
| 稳定性 | 单元测试较多，近期修了多处生命周期问题；缺少长扫/真机/性能矩阵 | 6/10 |
| 工程发布 | 有 iOS CI 雏形，但签名、TestFlight、崩溃、性能、仓库分层不足 | 4/10 |
| 商业运营 | 隐私、用户支持、试用/订阅、客户验收报告基本未成体系 | 2/10 |

综合判断：5/10 到 6/10 之间。适合演示、试点、研究验证；还不适合直接作为收费生产工具推广。

## 现在不该继续做什么

1. 不该继续无目标地“发现一个小问题就修一个小问题”。
2. 不该继续加新功能，例如更多地图、更多导出格式、更多模型路线。
3. 不该在没有真实样本的情况下继续调估算公式，让数字看起来更好。
4. 不该把模拟器启动成功当成 LiDAR 扫描成功。
5. 不该让论文、训练实验、App 交付物继续混在同一层级里。

## 必须先做的 P0

这些是商业级前必须完成的，不建议跳过。

### P0.1 冻结主流程

只保留并打磨一条主路径：

新建扫描 → 选择树体/地块 → 真机扫描 → 停止录制 → 质量判断 → 完成估算 → 保存记录 → 查看历史/导出。

验收标准：

- 新用户不看说明也能完成一次扫描。
- 每一步只有一个明确主按钮。
- 失败状态有明确恢复动作。
- 扫描中、估算中、结果页、退出页不会互相抢状态。

### P0.2 真实设备验收矩阵

建立一个固定表格，每次发版都跑：

- LiDAR readiness 正确；
- 相机权限拒绝/恢复正确；
- 定位权限拒绝/恢复正确；
- 点云数量增长；
- 覆盖率达到 60% 和 85%；
- 录制 30 秒、60 秒、120 秒不崩；
- 后台切换后不会丢扫描；
- 估算完成后记录持久化；
- 历史打开点云不崩；
- 导出 PLY/CSV 可被外部工具读取。

### P0.3 真实果园 ground truth

商业可信度必须来自数据，不来自界面。

最小数据集建议：

- 至少 30 棵树；
- 至少 2 个品种或明确只支持 1 个品种；
- 每棵树记录人工果数或采摘重量；
- 每棵树至少 2 次扫描，用于判断重复性；
- 记录光照、遮挡、树高、冠幅、扫描时长、点云数量、覆盖率。

必须输出：

- MAE；
- MAPE；
- 置信区间；
- 失败案例分类；
- 哪些场景不支持。

### P0.4 仓库清理

商业交付仓库建议拆成：

- `app/` 或当前 iOS App 仓库；
- `model-training/` 训练实验仓库；
- `research-paper/` 论文资料仓库；
- `datasets/` 或外部数据存储；
- 大文件通过 Git LFS 或对象存储管理。

训练 runs、论文、第三方 research skill、数据集和本地派生数据不应该长期和 App 源码混在根目录；当前整理已先完成同仓内分区，后续可再拆独立仓库或外部对象存储。

### P0.5 发布质量门槛

CI 至少需要：

- Debug simulator build；
- Release generic iOS build；
- 全量 XCTest；
- SwiftLint 或等效静态检查；
- 项目文件一致性检查；
- 大文件/敏感文件扫描；
- TestFlight archive/signing 流程。

## P1：商业 MVP 打磨

P0 完成后再做这些。

1. 扫描页主流程视觉再收敛：减少同时出现的入口，突出“开始/停止/完成/补扫”。
2. 结果页改成“可信度报告”，让用户知道为什么可信或为什么需要复核。
3. 历史记录增加“待复核/已确认/已导出”的清晰状态。
4. 导出报告模板固定化：PDF/CSV/PLY/元数据一套对应同一记录。
5. 增加真实设备日志与崩溃收集。
6. 给校准数据建立闭环：人工实测 → 校准 → 下一次估算可追踪。

## P2：以后再做

这些不是现在的商业级关键路径：

- 更多 3D 格式导出；
- 复杂地图系统；
- 团队协作；
- 云同步；
- 订阅计费；
- 多语言营销页；
- 大规模架构拆分；
- 更多水果模型。

## 建议的 4 周路线

### 第 1 周：停止扩展，做主流程验收

- 固定主流程脚本；
- 真机跑 10 次；
- 记录每次失败；
- 只修阻断主流程的问题。

### 第 2 周：真实样本采集

- 扫 10-15 棵树；
- 每棵树做人工果数或称重；
- 计算误差；
- 分类失败原因。

### 第 3 周：结果可信度与复核

- 把结果页改成“估算 + 证据 + 复核建议”；
- 对低置信度结果明确标记；
- 给导出数据加质量字段。

### 第 4 周：仓库和发布门槛

- 清理仓库；
- 固化 CI；
- 准备 TestFlight；
- 写客户试点说明；
- 输出第一份真实果园验证报告。

## 下一步建议

下一步不要继续修小 bug。建议执行一个商业级 readiness sprint：

1. 创建 `REAL_DEVICE_ACCEPTANCE.md`，定义真机验收表。
2. 创建 `GROUND_TRUTH_PROTOCOL.md`，定义真实果园采样和误差计算。
3. 只修验收表中阻塞主流程的问题。

如果要我继续动手，建议从 `REAL_DEVICE_ACCEPTANCE.md` 开始，而不是继续在代码里找边角问题。
